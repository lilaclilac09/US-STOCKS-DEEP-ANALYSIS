# Data Model

The app reads structured content from three files in `data/`. Each file has a JSON Schema in [`data/schema/`](../data/schema/) that defines its shape.

## Files at a glance

| File | What it is | Schema |
|------|------------|--------|
| `data/companies.json` | The equity universe shown as cards in the UI. | [`companies.schema.json`](../data/schema/companies.schema.json) |
| `data/indexes.json` | Benchmark indexes (S&P 500, NASDAQ-100, etc.) for comparison views. | [`indexes.schema.json`](../data/schema/indexes.schema.json) |
| `data/sources.json` | Registry of external data providers (price feeds, fundamentals APIs). | [`sources.schema.json`](../data/schema/sources.schema.json) |

A handful of other files live in `data/` but are runtime caches or refresher output, not curated content:

- `data/cislunar.json`, `data/fundamentals.json` — generated by the Python refreshers in `scripts/`
- `data/price-alert-state.json` — written by `scripts/price-alerts.mjs`

Those are intentionally schema-less because they are machine-managed.

## Relationships

```
companies.json                indexes.json
        |                          |
        +---- (compared against) --+
        |
        v
sources.json   ── lists providers that refresh prices into companies.json
        |
        v
.env / GitHub Actions secrets   ── apiKeyEnv names the variable holding each key
```

The `apiKeyEnv` field in a source entry refers by name to an environment variable (e.g. `FMP_API_KEY`). See [security.md](security.md) for where each variable should live.

## Conventions worth knowing

### Symbols

- Uppercase (`NVDA`, `MSFT`).
- Non-US listings may carry an exchange suffix (`3105.TPEX`, `268A.T`).
- Symbols must be unique across `companies.companies` (enforced by `scripts/validate-data.mjs`). Uniqueness is not enforced against `taiwanReferenceOnly` because those entries shadow primary symbols on purpose.

### `currentPrice` is a string, not a number

Stored as a display string with currency prefix or suffix because the format varies by listing: `"$892.00"`, `"SEK 12.50"`, `"€3.80"`. Live prices from Finnhub are formatted into the same string shape before being written back.

### Category vs sector

- `sector` is a free-form descriptive label intended for humans (e.g. `"AI Accelerators"`, `"Memory / HBM"`).
- `category` is a machine grouping that drives card placement in the UI. Observed values today: `ai-hyperscalers`, `chokepoints`, `ai-software`, `semis`, `cpo-light`, `pcb-ccl`, `watchlist`. Adding a new value is intentional and does not need a schema change (the field is `string`, not an enum), but the UI must learn about it before cards will render.

### IDs

`indexes[*].id` and `sources[*].id` are lowercase, snake_case or kebab-case, and must be unique within their file. The schemas enforce the character class; the validator enforces uniqueness.

### `status` enums

| File | Field | Values |
|------|-------|--------|
| companies | `status` | `active`, `inactive`, `delisted`, `suspended` |
| indexes | `status` | `tracked` (surfaced in UI), `watch` (monitored only), `removed` (kept for history) |
| sources | `status` | `active`, `planned` (not yet wired), `deprecated` |

## How to add a new entry

1. Open the relevant `data/*.json`.
2. Add a new object that satisfies the schema. The schemas mark every observed field as `required` and forbid unknown fields (`additionalProperties: false`) so typos are caught.
3. Run `npm run validate:data`.
4. Commit.

If you genuinely need a new field, add it to the schema in the same commit. Reviewers should reject schema-less additions.

## Validation

```bash
npm run validate:data
```

Today the script (`scripts/validate-data.mjs`) does structural checks and uniqueness enforcement, but does not yet read the JSON Schemas — it has its own hand-rolled checks that overlap. A follow-up should wire the script through `ajv` so the schemas become the single source of truth. The current overlap is intentional: schemas describe the shape declaratively for humans and tools (editors get autocomplete; CI can run them via `ajv-cli`), while the script enforces the cross-record invariants (duplicate-symbol detection) that schemas do not express.

For manual one-off validation without adding a dependency:

```bash
npx -y -p ajv-cli@5 -p ajv-formats@3 ajv validate \
  -s data/schema/companies.schema.json \
  -d data/companies.json \
  -c ajv-formats --spec=draft2020 --strict=false
```
